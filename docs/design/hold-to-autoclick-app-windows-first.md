# Hold-to-autoclick app, Windows first

saw-auto-clicker's first release: a small background app that turns a held mouse button into rapid clicks. Windows ships first. The core is built so macOS and Linux backends can be added later without reworking it.

## Problem

Some tasks need sustained rapid clicking, which is tiring and uneven by hand. Existing auto-clickers are mostly "start clicking at a point until stopped". They don't follow the user's own hand: the user can't press normally, hold to auto-click, and release to stop. They also click with perfectly even timing.

## Goals

- **Hold-to-click.** While the app is armed, holding the left or right button longer than a configured delay starts auto-clicking that button at a target clicks-per-second (CPS). Releasing the button stops it.
- **Normal input stays normal.** A press shorter than the delay, and any input while the app is disarmed, reaches applications unchanged. While armed, *any* hold longer than the delay auto-clicks, including drags, text selection and long-presses. That is intended, and the hotkey exists so the user can disarm for that kind of work; the README says so.
- **Small and in the background.** A tray icon, a small settings window, a global hotkey that toggles armed/disarmed, and optional start at login.
- **Jitter.** An optional setting that varies click timing so clicks aren't perfectly uniform, without changing the average rate.
- **Portable core.** Platform code sits behind a narrow backend interface, so macOS and Linux are additions rather than rewrites.

## Non-goals

- macOS and Linux backends in this project (R19, R20 are deferred; the design for them is recorded in C9–C12 so the interface accommodates them).
- Clicking into elevated (administrator) windows. See C5 and Q4.
- Touchscreen and pen input. Only physical mouse buttons and touchpad clicks are in scope.
- Clicking at a fixed screen point, recording macros, or scheduled clicking.
- Middle and side buttons.
- Code signing. See Q6.

## Constraints

Checked 2026-10-23 against primary sources. Re-run the method if the world may have moved.

- **C1. A Windows low-level mouse hook sees every button press on the desktop, and its callback must return fast.** `SetWindowsHookExW(WH_MOUSE_LL)` covers all threads on the caller's desktop (not the UAC secure desktop or lock screen) and runs the callback on the installing thread, which must pump messages. If the callback overruns `LowLevelHooksTimeout` (capped at 1000 ms on Windows 10 1709+; Microsoft documents no default, third parties report 300 ms), Windows passes the event on and, on Windows 7+, removes the hook silently with no way to detect it. Method: https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc
- **C2. `LLMHF_INJECTED` marks input injected by *any* process, not just this one.** Mouse-remapping software, remote desktop and other macro tools also set it, so a genuine physical press can arrive flagged as injected. `MSLLHOOKSTRUCT.dwExtraInfo` carries the value the injector put in `MOUSEINPUT.dwExtraInfo`, so an app can tag its own injected events and recognise them exactly. Method: https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-msllhookstruct
- **C3. Default Windows timer granularity is too coarse for high CPS; a high-resolution waitable timer is not.** The default tick is about 15.6 ms (Intel VTune docs; no current Microsoft page states it). `CreateWaitableTimerExW` with `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` (Windows 10 1803+) exists for "short expiration delays on the order of a few milliseconds". On Windows 11, `timeBeginPeriod` is not honoured for a process whose windows are all invisible, which is exactly a tray-only app, unless it opts out via `SetProcessInformation(ProcessPowerThrottling)` with `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION`. Method: https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw, https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod
- **C4. `RegisterHotKey` gives a system-wide keyboard hotkey and fails when another app holds the combination.** It delivers `WM_HOTKEY`, accepts keyboard virtual-key codes only (not mouse buttons), reserves F12, and supports `MOD_NOREPEAT`. Method: https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey
- **C5. A non-elevated process cannot click into an elevated window, and fails silently.** `SendInput` is subject to UIPI: injection into a higher-integrity window is blocked, and neither the return value nor `GetLastError` reports it. Whether the hook still sees the physical button while an elevated window has focus is undocumented; AutoHotkey's FAQ reports it does not, and the R16 run on the test VM agreed: a press aimed at an elevated window never reached the non-elevated hook. The fixes are running elevated, or `uiAccess` with a signed binary installed under Program Files. Method: https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput, https://www.autohotkey.com/docs/v2/FAQ.htm
- **C6. How touchpad clicks and taps reach `WH_MOUSE_LL` is undocumented.** Microsoft documents a signature for pen/touch-promoted mouse messages (`GetMessageExtraInfo() & 0xFFFFFF00 == 0xFF515700`) for window messages only, and says nothing about precision-touchpad clicks or taps at the hook. Method: https://learn.microsoft.com/en-us/windows/win32/tablet/system-events-and-mouse-messages. Must be checked on hardware (R13).
- **C7. The `windows` crate exposes every Win32 call the Windows backend needs.** In `windows` 0.62.2: `SetWindowsHookExW`, `MSLLHOOKSTRUCT`, `LLMHF_INJECTED` (`Win32_UI_WindowsAndMessaging`); `SendInput`, `RegisterHotKey` (`Win32_UI_Input_KeyboardAndMouse`); `CreateWaitableTimerExW`, `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` (`Win32_System_Threading`). Upstream master is reorganising module paths, so expect churn on upgrade. Method: grep of the published 0.62.2 crate source.
- **C8. Of the cross-platform input crates, `rdev` doesn't fit and the tauri-apps crates do, partly.** `rdev`'s last release is 0.5.3 (2023-06-26); its events carry no injected/physical marker, and its released `listen` does not work on Wayland. `tray-icon` (0.26.1, 2026-10-07) supports Windows, macOS and Linux via AppIndicator/KSNI. `global-hotkey` (0.9.0, 2026-10-16) supports Windows, macOS and X11 only. Method: https://github.com/Narsil/rdev, https://github.com/tauri-apps/tray-icon, https://github.com/tauri-apps/global-hotkey
- **C9. (macOS, for R19.)** `CGEventTapCreate` observes global mouse events. An active tap and `CGEventPost` both require Accessibility permission (preflight via `CGPreflightPostEventAccess`). A tap that stalls is disabled with `kCGEventTapDisabledByTimeout` and must be re-enabled with `CGEventTapEnable`. Own events are recognised by tagging `kCGEventSourceUserData`, not by source state, which posters can set to match hardware. `kCGMouseEventClickState` is documented, but whether synthetic pairs need it set explicitly is not. Method: CGEvent.h / CGEventTypes.h in the macOS SDK; WWDC19 session 701.
- **C10. (Linux/X11, for R20.)** XInput2 raw events or XRecord observe global button presses; XTest injects them. Under Xwayland they reach X clients only. Method: X.Org protocol docs.
- **C11. (Linux/Wayland, for R20.)** Wayland has no way for an ordinary client to observe global input. The `InputCapture` portal triggers only on pointer-barrier crossings. Injection is possible through the `RemoteDesktop` portal (libei, with a consent dialog) and hotkeys through the `GlobalShortcuts` portal. Method: https://flatpak.github.io/xdg-desktop-portal/docs/
- **C12. (Linux, either session, for R20.)** Reading `/dev/input/event*` via evdev and re-emitting through `uinput` works under both X11 and Wayland. It needs read access to the event nodes (the `input` group on most distros) and write access to `/dev/uinput` (usually root-only), and `EVIOCGRAB` takes the device away from every other reader. Method: https://www.kernel.org/doc/html/latest/input/uinput.html
- **C13. Testing runs in a Windows on ARM VM on an Apple Silicon Mac; there is no Windows touchpad hardware.** The Mac's trackpad reaches the VM as an ordinary pointing device, so the VM cannot exercise C6's precision-touchpad path. Timing measured in a VM can differ from bare metal, which is why A4 repeats the key checks on a physical x64 PC. Method: operator, in session 2026-10-23.

## Requirements

### Behaviour (core, platform-independent)

- **R1.** Settings are **CPS**, **activation delay**, **Jitter**, and the **toggle hotkey**. One CPS/delay/Jitter set applies to both buttons. Ranges and defaults per Q1–Q3.
- **R2.** The hotkey toggles armed/disarmed. Disarmed, the app starts no new burst, and every physical event outside a burst reaches applications unchanged. Disarming during a burst stops new injections at once; that button's burst still ends at its physical release under D7, so R6 holds.
- **R3.** Armed, a physical button press reaches applications immediately. If the button is released before the activation delay, the press-and-release is exactly what the user did: clicks, double-clicks and short drags behave normally.
- **R4.** Armed, if the button is still held when the activation delay elapses, the app clicks that button at the target CPS until the physical release. Only a press that begins while armed qualifies: a button already held when the app is armed starts no burst until it is pressed again ([3-D1](https://github.com/dbaggott/saw-auto-clicker/issues/3#issuecomment-6387312834)).
- **R5.** Left and right run independently. Holding both auto-clicks both; releasing one stops only that one.
- **R6.** The logical button state never ends up stuck. After the physical release, applications have received exactly one final button-up, and nothing is injected for that button afterwards. This holds when the release lands at any point in the click cycle, including while an injection is in flight (either order of arrival at the hook), when the user disarms mid-burst, when the user quits mid-burst (D7), and when the hook dies mid-burst (D8), with the physical release landing before or after detection, where the one permitted deviation is a single redundant up, never a stuck button. Each of these is a unit case under R9.
- **R7.** With Jitter at 0, intervals are as uniform as the timer allows. With Jitter J above 0, consecutive click intervals vary randomly within ±J of the nominal interval, and the share of each interval the button spends up varies too, exactly as D5 defines. Over any N ≥ 25 consecutive intervals, the mean interval is within 2% of the nominal interval T, at any J ≤ 0.5.
- **R8.** Measured on the test VM (C13), a 10-second hold at any CPS in the supported range delivers a mean rate within ±5% of the target, with Jitter at 0 (A1).
- **R9.** The core (button gate, scheduler, Jitter) is driven entirely through the backend interface (D2) and a clock abstraction, so it is unit-tested with a fake backend and fake clock, without an OS. The tests include every case R6 lists, each in both arrival orders where order can vary, and D8's skipped-deadline case: an up that echoes after its paired down's deadline has passed (spec review round 3, observation 3-O1 on https://github.com/dbaggott/saw-auto-clicker/issues/1).

### Windows backend and app

- **R10.** Physical presses are recognised by excluding the app's own tagged events (D3), not by `LLMHF_INJECTED` alone (C2). Input injected by other software, such as a remapping driver, is treated as physical.
- **R11.** The hook runs on a dedicated thread that does nothing but pump messages and run the callback, never the tray or settings-window thread. The callback calls the core's button gate (D2), returns its pass/suppress answer, and posts the event to the scheduler without blocking; it does no timing, injection or waiting (C1). The app detects and recovers from a removed hook per D8.
- **R12.** Click timing uses a high-resolution waitable timer scheduled against absolute deadlines, so per-click error does not accumulate (C3). The process also opts out of Windows' background power throttling (`SetProcessInformation(ProcessPowerThrottling)`, covering execution-speed/EcoQoS throttling, which is the kind more likely to slow a tray-only app, as well as timer resolution). Whether either opt-out is needed alongside the high-resolution timer was left to A1. As built, both opt-outs are applied, each separately, and a refused one does not stop startup. A1 on the VM found no measurable difference at 50 CPS with either or both turned off, but the VM ran on mains power with no power-saving mode, which is where Windows throttles hardest, so both are kept (decision log, 2026-10-24).
- **R13.** Clicks from the Mac trackpad, as the test VM receives them, auto-click like a mouse button. Behaviour on a Windows precision touchpad is unverified (C6), and the README says so.
- **R14.** A tray icon shows armed vs disarmed at a glance. Its menu has Arm/Disarm, Settings…, Start at login, and Quit. The settings window edits R1's settings, applies them without a restart, and persists them across restarts in a per-user config file. It also sets whether the app arms on startup, off by default; the armed state at quit is not remembered. The first run after the first install, when there is no config file yet, starts armed and writes the file. Reinstalling or upgrading keeps the file.
- **R15.** If the hotkey can't be registered (C4), the settings window says so and the previous working hotkey stays in effect. A hotkey whose key is a letter or digit must include Ctrl, Alt or Win, since registering it bare would stop that key typing in every app. The settings window rejects one as a validation error before registering anything, so the previous hotkey stays in effect, and the config loader replaces one with the default ([5-D1](https://github.com/dbaggott/saw-auto-clicker/issues/5#issuecomment-6387886218), [refined](https://github.com/dbaggott/saw-auto-clicker/issues/5#issuecomment-6387896266)).
- **R16.** The app never starts or continues a burst into a window it can't inject into (C5). The *target* is the top-level window under the cursor, checked when the delay elapses and again before each injected up. If the target's process runs at a higher integrity level than the app, or its integrity can't be read, the burst does not start, or ends at that point, with the button logically down so the physical release closes it under D7. The tray tooltip then says clicking is unavailable over elevated windows. As observed on the VM, a press that starts over an elevated window never reaches the hook (C5), so it gets no burst and no tooltip line: Windows delivers it as one normal press. The target check and the tooltip cover a burst that moves onto an elevated window, which follows from the code but was not run (decision log, 2026-10-24). The target is read with `GetAncestor(WindowFromPoint(cursor), GA_ROOT)`, and its integrity level with `OpenProcessToken` and `GetTokenInformation(TokenIntegrityLevel)`, in `crates/windows/src/target.rs`.
- **R17.** Start at login uses the per-user `HKCU\…\Run` key, so neither installing nor enabling it needs administrator rights.
- **R18.** CI builds and tests on `windows-latest` behind a `ci-required` umbrella job. A push to main whose workspace version has no release yet publishes `v<version>` with one Windows installer as its GitHub release asset. The installer carries both the x64 build, for physical PCs, and the arm64 build, for Windows on ARM such as the test VM (C13), and installs the one native to the machine. CI installs and uninstalls it on an x64 and an Arm64 runner, checking each got its own build. Bumping the version in `Cargo.toml` is how a release is cut, and the installer carries the binaries CI built for that commit (https://github.com/dbaggott/saw-auto-clicker/pull/13). CI also runs clippy and the `saw-core` tests on macOS, so the develop-on-any-host promise is checked ([2-D1](https://github.com/dbaggott/saw-auto-clicker/issues/2#issuecomment-6387072427)), and the release runs after CI's own build and test jobs ([6-D1](https://github.com/dbaggott/saw-auto-clicker/issues/6#issuecomment-6388121611)). The release checks that the x64 app launches on the runner; the arm64 ones were checked by hand on the VM on 2026-10-24 (`saw-app --version` prints `saw-app 0.1.0` and exits 0, `saw-measure` with no arguments prints its usage and exits 1).

## Decisions

- **D1. Rust, using the `windows` crate directly for the hook, injection, timer and hotkey.** Because: the single small binary with no runtime suits a background app, and Rust reaches the native APIs on all three platforms equally well; `rdev` can't distinguish injected from physical input and is unmaintained (C8), and that distinction is the core of the design. Revisit if: a maintained cross-platform crate appears that exposes per-event injection tags and a grab.
- **D2. A narrow backend interface with three capabilities: observe button events and apply the core's pass/suppress answer to each, inject button down/up tagged as the app's own, and register a toggle hotkey. The pass/suppress answer comes from the core's *button gate*: a pure, non-blocking function the backend calls synchronously inside its callback, over per-button state that only the observing thread mutates (D7).** The gate also emits each event onto a non-blocking queue for the scheduler thread, which owns timing and calls inject. Because: these are the only parts that differ by OS (C1–C12), and a seam this narrow lets the core be tested with fakes (R9). The decision must be synchronous because the hook has to answer before returning, and the scheduler can't be waited on (C1); C9's tap callback and C12's grab-and-re-emit loop have the same shape, so the gate ports unchanged. Revisit if: the macOS or Linux backend needs a capability these three can't express.
- **D3. Own events are tagged with a fixed magic value in the injection's extra-info field (`dwExtraInfo` on Windows, `kCGEventSourceUserData` on macOS), and the hook ignores tagged events.** Because: `LLMHF_INJECTED` and macOS source state both mark *any* injector (C2, C9), which would misread a user on remapping software as "not pressing". Revisit if: none identified.
- **D4. The click cycle is "inject up, wait the up-time, inject down, hold until the next deadline", where the up-time is 40% of the nominal interval, starting from the logically-down state the physical press created, and ending logically down so the physical release supplies the final up.** How the burst ends, in every arrival order, is D7. Because: the user's own press and release then bracket the burst, so no button is ever left down, and any hold shorter than the delay is untouched (R3). Revisit if: an application reacts badly to the up/down pattern, e.g. treats the first injected up as the end of a drag it then cancels.
- **D5. Jitter J is a fraction from 0 to 0.5 (shown as 0–50%). With nominal interval T, click k's down is scheduled at kT + o_k, where o_k is drawn uniformly from ±(J/2)·T, so consecutive intervals g_k fall within T(1 ± J), i.e. between 0.5T and 1.5T at the cap. The up-time before that down is g_k · u_k, with u_k drawn uniformly from [0.4 − 0.2J, 0.4 + 0.2J], so at most 0.3–0.5 of the interval at the cap. The up-time and the down-hold are each clamped to at least 2 ms.** Because: offsets drawn around a fixed grid never accumulate, so the mean of N consecutive intervals differs from T by (o_{k+N} − o_k)/N, at most J·T/N, which is R7's 2% at N = 25 and J = 0.5 (counted in intervals, not seconds, because at low CPS a second holds too few intervals for any bound); capping J at 0.5 keeps every interval at least 0.5T long, and scaling the up-time by the actual interval keeps it positive and inside its own cycle. The 2 ms floors only come into play near Q1's ceiling. Revisit if: users find uniform jitter still looks mechanical (a Gaussian draw is the next option), or Q1's ceiling rises enough that the floors distort the rate.
- **D6. Windows first; macOS and Linux follow the Windows release.** Because: Windows is the primary target, and the D2 interface designed against all three keeps the later ports additive. Revisit if: a macOS or Linux user need appears before the Windows release.
- **D7. The button gate tracks, per button, the *delivered* state (the last down or up that passed the hook: unknown, down or up) and a *released* flag. It applies these rules, armed or not:**
  - **physical down:** pass; delivered = down; released = false.
  - **physical up:** pass if delivered is down or unknown, and set delivered = up; suppress if delivered is already up. Either way, set released = true.
  - **tagged (own) event:** suppress if released; otherwise pass and set delivered to it.

  **The scheduler stops a button's burst when it sees that button's physical up, and injects nothing for it afterwards. On quit with a burst active and delivered up, the app injects a tagged down and waits up to 100 ms for the gate to pass it before unhooking, so the physical up that follows still closes the burst.** Because: the hook sees every event, its own and the user's, in one serial order, so state kept there is exactly what applications received. Both in-flight orders resolve to exactly one final up. Physical up first: tagged events still in flight are suppressed. Tagged up first: the physical up is suppressed and any tagged down after it is too. Disarming needs no special case, because the scheduler stops and the gate closes the burst. Outside a burst no tagged events exist, so every physical event passes. Revisit if: an OS backend can't observe its own injected events in order with physical ones (macOS and Linux designs both can, C9, C12).
- **D8. Hook death is detected by liveness during a burst and handled by reinstall when idle.** Injection is lockstep: the scheduler injects a button's next event only once its deadline has arrived *and* the previous injection for that button has echoed back through the gate (a deadline missed while waiting is not caught up; the next one follows the grid). A skip drops a whole up/down cycle, never one event: when an up echoes after its paired down's deadline has passed, that down goes out as soon as the up echoes, the next up waits for its own grid deadline, and ups and downs for a button strictly alternate (spec review round 3, observation 3-O1 on https://github.com/dbaggott/saw-auto-clicker/issues/1). If an injection hasn't echoed within max(250 ms, 2 × the nominal interval), the scheduler treats the hook as dead: it stops the burst; if that unechoed injection was a down, it injects one up; then it injects nothing further, reinstalls the hook, and resets every button's delivered state to unknown so the next physical up passes. The reset runs on the observing thread as part of the reinstall, between the unhook and the install, so D2's rule that only the observing thread mutates gate state holds, and the reset is ordered before the new hook's first event (spec review round 4, 1-O6 on https://github.com/dbaggott/saw-auto-clicker/issues/1). While idle (armed, no burst running; a button held without a burst counts as idle, so a release lost to a dead hook can't hold reinstall off forever, [3-D1](https://github.com/dbaggott/saw-auto-clicker/issues/3#issuecomment-6387312834)), the app reinstalls the hook on every arm and every 60 s, unhooking the old one before installing the new one, so the gate never sees an event twice. Because: C1 removes a stalled hook silently, but during a burst the missing echo of the app's own tagged events makes it detectable, and that's when an undetected death would mean runaway clicking. Lockstep means at most one injection per button can reach applications unseen after the hook dies, so a release inside the detection window is followed by no further clicks. The only correction is an up, never a down: the user may already have released, so a down could leave the button stuck, while the worst case of an up is one redundant up, which applications ignore. While idle, a dead hook only means holds stop auto-clicking, which fails safe, so a short gap during reinstall costs nothing. Revisit if: injection blocked by UIPI (C5) also fails to echo and trips this check in normal use; R16 is meant to keep bursts away from such windows.

## Open questions

- **Q1. What CPS range is supported?** Built at the default: 1–50, default 10, because D4's up-time and C3's timer resolution both get tight above ~50, and most applications process input slower than that anyway. A1 confirmed it: 50 CPS held within 0.3% on the VM.
- **Q2. What activation-delay range is supported?** Built at the default: 50–2000 ms, default 250 ms, because under ~50 ms ordinary clicks start triggering auto-clicks, and 250 ms is long enough that a normal click never engages but short enough not to feel laggy.
- **Q3. What's the default hotkey?** None: the user chooses one in the settings window. It was built at Ctrl+Alt+F8 first, and the settings window still ticks Ctrl and Alt when it opens with no hotkey set, because F-keys with two modifiers rarely collide with apps or games, and F12 is reserved (C4).
- **Q4. Should the app offer to run elevated, so it works over admin windows?** Built at the default: no, because running a global input hook elevated widens what a bug can do, and the target use doesn't need it; R16 keeps bursts out of elevated windows instead, and the README documents the limitation.
- **Q5. How does the app recover from a silently removed hook (C1)?** Decided 2026-10-23 (D8).
- **Q6. Is the Windows release signed?** Built at the default: no; release unsigned, and the README documents the SmartScreen prompt and the possibility (unverified) that Defender flags an unsigned binary that hooks the mouse and injects input, with how to allow it. Because a certificate costs money and the audience is small. Revisit before wider distribution, or if Defender flags the release build.
- **Q7. Which Linux approach does R20 take?** Still open, with R20 deferred. Default: evdev + uinput (C12), because it is the only way to observe the held button under Wayland (C11), and it also works on X11; it needs a one-time `input`-group/udev setup that the README documents.
- **Q8. What does the settings window use?** Built at the default, confirmed in https://github.com/dbaggott/saw-auto-clicker/pull/10 (a `--self-test` on the Windows CI runner opens the settings window twice beside the tray), so the Win32 fallback was not needed. Default: `eframe`/`egui`, opened on demand alongside `tray-icon`, because both run on all three platforms and egui needs no web runtime.
- **Q9. What licence?** Built at the default: MIT, because the repo is public and it's the common default for small Rust tools.

## End-to-end acceptance criteria

The paths below use the workspace layout https://github.com/dbaggott/saw-auto-clicker/issues/2 creates: `crates/core/` (button gate, scheduler, Jitter), `crates/windows/` (Windows backend), `crates/app/` (the tray app binary) and `crates/measure/` (a dev binary that arms with fixed settings and logs the timestamp of every tagged down the gate *passes*, i.e. every click applications received, leaving out suppressed events).

- **A1.** On the test VM (C13), running the arm64 build of `crates/measure/`, holding left for 10 s at 10, 20 and 50 CPS (Jitter 0) gives a mean measured rate within ±5% of target each time, computed from the logged passed downs (the gate's view; R10's tagging makes that the same set applications received), and at Jitter 30 (held at 20 CPS) within ±5% with visibly varied intervals. Proves the scheduler and the Windows timer hit the rate under real conditions. **Recorded by https://github.com/dbaggott/saw-auto-clicker/issues/4 on its PR.** If the VM misses the tolerance, A4's bare-metal run decides whether the app or the VM is at fault. Re-run after a change under `crates/core/` or `crates/windows/`, unless the PR's record shows the change leaves scheduling and timing as they were. Contributes: R4, R7, R8, R12. Built by https://github.com/dbaggott/saw-auto-clicker/pull/8 and https://github.com/dbaggott/saw-auto-clicker/pull/9; steps recorded in https://github.com/dbaggott/saw-auto-clicker/pull/9. **Result, 2026-10-24: pass**, on the arm64 CI build of `main` at `9d7e2ad`, held on the Mac trackpad: 10 CPS +0.1%, 20 CPS +0.2%, 50 CPS +0.0% and −0.3%, interval sd 1–4 ms; Jitter 30 at 20 CPS +0.0%, sd 6.6 ms against 1.3 ms at Jitter 0, intervals 30–70 ms. A first set ran 10 CPS fast because `saw-app` was also running and armed: both programs use the same tag, so each logs the other's clicks as its own. Those runs were discarded and repeated with the app closed.
- **A2.** On the test VM, running the arm64 build of `crates/app/`, a scripted pass: a short click, a double-click and a short drag behave normally; holding both buttons auto-clicks both; releasing at 20 random points during bursts at 10 and 50 CPS never leaves a button stuck (the next physical click behaves normally); disarming with the hotkey mid-hold stops clicking and the release behaves normally; quitting from the tray menu while the other button is in a burst leaves it unstuck; with Ctrl+Alt+F8 already registered by another process, choosing it in settings shows R15's message and the previous hotkey keeps working.
